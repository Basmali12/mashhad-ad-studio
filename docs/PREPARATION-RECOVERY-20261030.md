# تجهيز حسابات المحركات — فحص وإصلاح محلي

## نتيجة الفحص

فحص خطة حساب Nor للقراءة فقط بتاريخ 2026-10-30 أعاد:

- عامل المصدر مطابق وجاهز: workerReady=true وexecutionReady=true.
- الحساب الجديد ليس جاهز الأوزان بعد؛ الخطة تعرض 71,442,240,044 بايت (نحو 66.54GiB).
- المسار modal-cpu-cloud، بدون GPU وبدون مرور الأوزان بقرص HostHatch.
- لم تُنفذ الخطة. لم تُكرر محاولة Nor القديمة أو تبدأ عملية مدفوعة جديدة.
- التجربة السابقة توقفت قبل تسجيل عامل التحقق وأي استدعاء لمعالجة الأوزان. السبب الأصلي الدقيق لم يُحسم؛ لا يجوز استنتاج أن التوكن غير صحيح، أو أن هذه الاختبارات المحلية أثبتت نجاح نقل الحساب فعلياً.

## الثغرات التي عولجت

1. كان استئناف متابعة مهام التجهيز بعد إقلاع الخدمة مرتبطاً بطلب صفحة state. أضيف مراقب بالخادم يعيد متابعة نفس المعرّفات المحفوظة دون الاعتماد على المتصفح؛ لا ينشئ عملية dispatch أخرى. مراجعة السجل كل 15 ثانية، ومحاولة استئناف المراقبة المتعثرة لا تتكرر أكثر من مرة بالدقيقة لكل مهمة.
2. كان فشل قراءة الحالة مرة واحدة يُنهي المراقبة ويصل إلى مسار إلغاء النقل. تعاد الآن قراءة نفس المهمة بتراجع زمني 3/6/12/24/30 ثانية ضمن الموعد النهائي الأصلي؛ لا تُعاد مرحلة النقل ولا تُمدد نافذة الإنفاق.
3. إغلاق الخدمة يفصل متابعة نقل CPU المعتمد، بدلاً من طلب إلغائه. زر الإلغاء الصريح والمهلة الأصلية يظلان قائمين، وسلوك إيقاف جلسات GPU لم يتغير. توقف الخادم نفسه لا يمنع استمرار مهمة Modal غير المتزامنة؛ لذلك لا يمثل غياب المراقبة إثباتاً على توقف الرسوم.
4. أضيف حفظ مراحل تجهيز عامل الحساب الجديد قبل تنفيذ كل خطوة، مع بثها للواجهة: فحص العامل، بناؤه، حفظ السجل، التحقق من الدالة، حفظ نقطة الاستئناف، جاهزية العامل. لا تُحفظ رسائل الاستثناء الخام أو الأسرار.
5. إذا فُقد الرد بعد نجاح تجهيز العامل، تستطيع المتابعة ربط العامل الموجود بعد تطابق البصمة ومعرّف الدالة. إذا تعذر إثبات وجوده، لا تبدأ بناءً مدفوعاً جديداً أو استدعاءً بديلاً تلقائياً.
6. الواجهة تعيد قراءة الحالة بعد انقطاع الاتصال، ولا تعتبر الحالة غير المحسومة نهاية مؤكدة. «جاهز» يتطلب اكتمال التحقق وREADY وتأكيد توقف موارد النقل.

## مسار المستخدم

إدخال الاسم وToken ID وToken Secret ← تحقق وحفظ مشفر ← فحص الأوزان ← خطة كلفة ← موافقة واحدة على الخطة المحددة ← تجهيز عامل الحساب وVolume ← فحص الموجود ونقل الناقص ← فحص البصمات وكتابة READY/RUNTIME ← تم التجهيز ← اختبار فيديو من الإدارة ثم نشر المحرك للزبائن.

إغلاق الصفحة لا يرسل إلغاء. تغيير GPU لا يقتضي نقل الأوزان المتوافقة من جديد. لا توجد جدولة لإعادة نقلها شهرياً. هذا لا يلغي كلفة التخزين الدائم.

الاستئناف المتاح للبيانات هو على مستوى الملفات السليمة المكتملة؛ لا ندعي استكمال بايتات ملف SDK غير مكتمل. لا توجد نسبة رفع داخلية مصطنعة: قياس source_bytes_hashed فحص مصدر، وليس رفعاً. خلال رفع لا يكشف SDK تقدمه يبقى المؤشر غير محدد حتى وصول إقرار حقيقي.

## التحقق المحلي

- 164 اختبار Node للخلفية: نجحت، ومنها إعادة إقلاع API بلا طلب متصفح، منع تكرار dispatch، فقدان رد الحالة، المحافظة على المهلة، وفصل المراقبة عند الإغلاق.
- 8 اختبارات واجهة AccountSetup: نجحت.
- 4 اختبارات Python: نجحت، تحاكي فشل تجهيز العامل وحفظ مرحلته، عدم تسرب رسائل الاستثناء، ربط نشر موجود، ورفض إعادة بناء غامضة. حدود SDK الشبكية مستبدلة في هذه الاختبارات.
- validate_transfer_images.py: نجح باستخدام Modal SDK المثبت، بدون hydrate/build سحابي أو تنزيل.
- TypeScript وESLint وبناء الزبون وبناء الأدمن: نجحت.
- لا اختبار GPU، لا نقل، لا إنشاء Volume جديد، لا تغيير فوترة.

## حدود التسليم

هذه تعديلات محلية غير منشورة بعد. النشر مؤجل احتراماً لطلب صاحب النظام إبقاء توليده الحالي يعمل. يتطلب النشر تحديث ملفات HostHatch والواجهة معاً، بعد التحقق من عدم وجود عمل نشط والاحتفاظ بنقطة استعادة. لا يلزم تغيير نموذج LTX أو الأوزان.

بعد النشر يلزم اختبار تجهيز Nor مضبوط بخطة جديدة وموافقة مرتبطة بها، ثم اختبار فيديو منفصل قبل اعتبار الحساب صالحاً للعملاء. نجاح الفحوص المحلية لا يثبت صلاحيات إنشاء الموارد أو رصيد الحساب أو نجاح بناء Modal. لا يمكن ضمان انعدام أخطاء مزود الخدمة؛ الحل يحفظ المهمة ويمنع التكرار ويوضح سبب التعطل بدلاً من إعلان نجاح وهمي.
